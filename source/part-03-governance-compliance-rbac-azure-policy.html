Part 3 — Governance & Compliance (RBAC + Azure Policy)

🎯 Goal: Understand how an enterprise controls security, access, cost, and compliance standards across Azure — this is one of the most heavily interviewed topics for any Azure role.

🗺️ Concept Map

flowchart TD Gov["Governance"] --> RBAC["RBAC\n(Who can do it?)"] Gov --> Policy["Azure Policy\n(What is allowed?)"] RBAC --> Built["Built-in Roles"] RBAC --> Custom["Custom Roles"] RBAC --> Scope["Scope"] RBAC --> Inherit["Inheritance"] Policy --> Def["Policy Definition"] Def --> Assign["Policy Assignment"] Assign --> Init["Policy Initiative"]

3.1 What is Governance?

Governance means creating rules and standards so everyone uses Azure correctly, securely, and consistently. It controls: Security, Access, Cost, Compliance, Resource Creation, and Naming Standards.

🏢 Real Project Example: 50 developers have Azure access. Without governance: one creates a VM in East US, another in Central India, someone spins up an oversized (expensive) VM, nobody follows a naming standard, nobody tags anything. Result: high cost, security gaps, and an unmanageable environment. Governance exists to prevent exactly this.

🧠 Interview Angle: "Azure Governance is the process of managing Azure resources by applying security, access control, policies, naming standards, and compliance rules across the organization."

3.2 RBAC (Role-Based Access Control)

RBAC controls who can do what in Azure. Instead of giving everyone full access, you assign roles based on job responsibility — this is the Least Privilege principle in action.

Team Can Cannot
Developer Create a VM Delete the Subscription
Network Team Manage VNets Access SQL Database
Database Team Manage SQL Modify Firewall

🧠 Interview Angle: "RBAC is used to control user permissions in Azure by assigning roles based on job responsibilities."

Built-in Roles

Role Permissions
Owner Full access + can assign roles to others
Contributor Full resource management, cannot assign roles
Reader Read-only — cannot modify anything
User Access Administrator Can manage RBAC only, nothing else

🧠 Interview Angle: "Difference between Owner and Contributor?" → "Owner has full access and can assign RBAC roles. Contributor can manage resources but cannot assign permissions to others."

Custom Roles

Sometimes built-in roles don't fit. Example: a support engineer should be able to Start / Stop / Restart a VM, but never Delete it — no built-in role matches that exactly, so you create a Custom Role.

🏢 Real Project Example: Support Team role — Allowed: Restart VM, Read Logs. Not Allowed: Delete VM, Delete Storage.

Scope & Inheritance

RBAC can be assigned at four levels, and permissions flow down automatically:

flowchart TD MG["Management Group"] --> Sub["Subscription"] Sub --> RG["Resource Group"] RG --> Res["Resource"] style MG fill:#0f766e,color:#fff

If you assign Reader at the Subscription level, that user automatically gets Reader on every Resource Group and Resource inside it — this is inheritance.

✅ Best Practice: Always assign RBAC at the highest suitable level — don't assign roles resource-by-resource; it doesn't scale.

3.3 Azure Policy

If RBAC answers "who can do it?", Azure Policy answers "what is allowed?" — it controls whether the resources being created actually meet company standards.

🏢 Real Project Example: Company rule: "Only Central India region allowed." A developer tries creating a VM in East US — Azure Policy blocks the deployment automatically, regardless of that developer's RBAC permissions.

RBAC Azure Policy
Controls User access Resource compliance
Answers Who can perform the action? What is allowed to be created?
Basis Identity-based Resource-based
Category Security Governance

Policy Definition → Assignment → Initiative

flowchart LR D["Policy Definition\n(the rule itself)"] --> A["Policy Assignment\n(activates the rule\nat a scope)"] A --> I["Policy Initiative\n(bundle of related\npolicies, assigned together)"]
  • Policy Definition — the rule, e.g. "Only Central India and South India regions are allowed."
  • Policy Assignment — a definition only takes effect once assigned to a scope (Subscription, Management Group, etc.).
  • Policy Initiative — a company might have 20 separate policies; instead of assigning each one-by-one, group them into one Initiative (e.g. a "Security Initiative" containing Allowed Regions + Mandatory Tags + Allowed VM Sizes + HTTPS Required + Storage Encryption) and assign it once.

🧠 Interview Angle: "An Initiative is a collection of multiple Azure Policies that can be assigned together."

Policy Effects

Effect Purpose
Deny Blocks the resource from being created
Audit Allows creation, but reports it as non-compliant
Append Adds extra properties automatically (e.g. a tag)
Modify Automatically updates resource properties
DeployIfNotExists Automatically deploys a missing required configuration
AuditIfNotExists Reports if a required configuration is missing
Disabled Turns the policy off

🏢 Real Project Example: Policy = "Mandatory Tag: Environment", Effect = Modify → Azure automatically adds the tag if it's missing, instead of just blocking the deployment.

3.4 Azure Blueprints (Legacy — Know It, Don't Lead With It)

⚠️ Azure Blueprints is no longer the primary governance tool for new environments — Microsoft now recommends Template Specs, Deployment Stacks, Azure Policy, and Infrastructure as Code (Terraform/Bicep) instead. Interviewers still ask about it because many existing enterprise environments were built with it.

Blueprints used to deploy a complete environment — RBAC + Policy + ARM Templates + Resource Groups — as a single package. Today, the same outcome is achieved with Azure Policy plus Infrastructure as Code.

3.5 Enterprise Governance Strategy

flowchart TD T["Tenant"] --> MG["Management Group"] MG --> S["Production Subscription"] S --> P["Policies"] P --> RG["Resource Groups"] RG --> R["Resources"]

Governance flows top-down. A real company requirement often looks like:

🏢 Real Project Example — Company Policy Requirement: - Only Central India region allowed - Only Standard VM sizes allowed - Every resource must be tagged: Environment, Project, Owner, CostCenter - No Public IP addresses allowed

Solution: RBAC → Developers get Contributor. Azure Policies enforce → Allowed Region, Allowed VM Size, Mandatory Tags, No Public IP. Everything is enforced automatically, with zero manual review needed.

✅ Part 3 Best Practices

  • ✅ Follow the Least Privilege principle always.
  • ✅ Use Security Groups, not individual users, for RBAC assignment wherever possible.
  • ✅ Apply RBAC at Management Group or Subscription level when appropriate.
  • ✅ Apply mandatory Tags via Policy, not manual process.
  • ✅ Group related rules into Policy Initiatives.
  • ✅ Keep Production and Non-Production strictly separate.
  • ✅ Use Infrastructure as Code (Terraform/Bicep) for consistent, repeatable deployments.

🖥️ Hands-On: Assign an RBAC Role in the Portal

  1. Navigate to a Resource Group (or Subscription) → select Access control (IAM) from the left menu.

  1. Select + Add → Add role assignment.

  1. Search for and select a role — e.g. Virtual Machine Contributor — then click Next.

  1. Under Members, select + Select members, search for the user or group, and add them.
  2. Select Review + assign twice to confirm.

💡 Try it yourself: Repeat this at the Subscription scope instead of a single Resource Group, and notice the role now applies to every Resource Group underneath — that's inheritance in action.

🧠 Part 3 — Interview Questions

What is Azure Governance?

The process of managing Azure resources by applying security, access control, policies, naming standards, and compliance rules consistently across the organization.

What is RBAC?

Role-Based Access Control — a system for controlling who can perform what actions on Azure resources, by assigning roles based on job responsibility instead of giving blanket access.

What is Azure Policy?

A governance tool that controls what resources can be created and whether they comply with organizational standards — independent of who is creating them.

What is the difference between RBAC and Azure Policy?

RBAC controls user access (identity-based — "who can do it"). Azure Policy controls resource compliance (resource-based — "what is allowed"). They work together, not instead of each other.

What are Built-in Roles?

Predefined Azure roles like Owner, Contributor, Reader, and User Access Administrator, covering the most common access patterns without needing custom definitions.

What is a Custom Role?

A role you define yourself when no built-in role matches a specific business requirement — for example, allowing VM restart but not VM deletion.

What is Scope in RBAC?

The level at which a role assignment applies: Management Group, Subscription, Resource Group, or individual Resource — from broadest to narrowest.

What is a Policy Initiative?

A collection of multiple related Azure Policy definitions that are grouped together and assigned as a single unit, instead of assigning each policy individually.

What is Azure Blueprint?

A legacy tool that packaged RBAC, Policy, ARM templates, and Resource Groups together to deploy a standardized environment in one go. Now largely replaced by Azure Policy plus Infrastructure as Code.

What is the Principle of Least Privilege?

Giving users only the minimum level of access required to do their job — nothing more — to reduce security risk.

🧩 Part 3 — Scenario-Based Questions

Developers are creating resources in different Azure regions, increasing latency and management complexity. How will you solve it?

I will create an Azure Policy that allows resource creation only in approved regions, such as Central India and South India, and assign it at the Management Group or Subscription level.

A support engineer needs to restart virtual machines but should not be able to delete them. What will you do?

I will create a Custom RBAC Role that allows Start, Stop, and Restart actions but excludes Delete permissions, then assign it to the support engineer.

Your company requires every Azure resource to have Environment, Owner, and CostCenter tags. How will you enforce it?

I will use Azure Policy with an appropriate effect — Modify for automatic remediation, or Deny to block non-compliant resources — and assign it at the Subscription or Management Group level.

A developer can create a VM but cannot assign permissions to another user. Why?

They most likely have the Contributor role, which can manage resources but cannot assign RBAC roles. Only Owner or User Access Administrator can manage role assignments.

A company has 80 Azure subscriptions. How would you apply the same governance rules to all of them?

I would organize the subscriptions under Management Groups and assign RBAC roles, Azure Policies, and Policy Initiatives at the Management Group level for centralized governance and lower administrative effort.

📋 Part 3 — Quick Revision

  • Governance = rules and standards for how Azure is used.
  • RBAC = controls who can perform actions.
  • Built-in Roles = Owner, Contributor, Reader, User Access Administrator.
  • Custom Role = built for a specific business need not covered by built-in roles.
  • Scope order = Management Group → Subscription → Resource Group → Resource.
  • Inheritance = permissions flow from parent to child automatically.
  • Azure Policy = controls what is allowed to be created.
  • Policy Definition = the rule. Assignment = activates it. Initiative = a bundle of rules.
  • Least Privilege = give only the minimum permissions needed.
  • Blueprint (legacy) = replaced today by Azure Policy + Terraform/Bicep.
