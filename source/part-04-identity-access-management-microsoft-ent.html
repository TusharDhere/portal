Part 4 — Identity & Access Management (Microsoft Entra ID)

🎯 Goal: Understand how users, applications, and automation tools securely authenticate and access Azure resources. IAM is a core Landing Zone pillar and a very frequent source of scenario-based interview questions.

🗺️ Concept Map

flowchart TD Id["Identity"] --> Entra["Microsoft Entra ID"] Entra --> User["Users"] Entra --> Group["Groups"] Entra --> SP["Service Principal"] Entra --> MI["Managed Identity"] Entra --> AppReg["App Registration"] AppReg --> EntApp["Enterprise Application"] Entra --> MFA["MFA"] Entra --> CA["Conditional Access"] Entra --> PIM["Privileged Identity\nManagement (PIM)"]

4.1 What is Identity?

Identity means who is trying to access an Azure resource. It can be a User, a Group, an Application, a Service Principal, or a Managed Identity. Azure always follows the same two-step check: first identify who you are, then check what you're allowed to do.

🏢 Real Project Example: Amit opens the Azure Portal. Azure first verifies "Who is Amit?" (authentication) — then checks "What can Amit access?" (authorization).

4.2 Microsoft Entra ID (formerly Azure Active Directory)

Microsoft Entra ID is Azure's Identity and Access Management service. It manages Users, Groups, Authentication, Applications, Service Principals, and Managed Identities — for the entire Tenant.

Responsibilities: User login, Authentication, MFA, Single Sign-On (SSO), Conditional Access, Identity Management.

🧠 Interview Angle: "Microsoft Entra ID is Azure's cloud-based Identity and Access Management service, used to authenticate users and manage access to Azure resources."

4.3 Users & Groups

A User represents a person (amit@company.com). Users can be: - Internal User — a company employee. - Guest User — an external person (vendor, client, consultant) — e.g. an external auditor given Reader access for one month.

A Group is a collection of users. Instead of assigning RBAC individually, assign it once to the Group — everyone in it inherits the access.

✅ Best Practice: Always assign RBAC to Groups, not individual users — it's easier to manage, less error-prone, and scales better.

4.4 Authentication vs Authorization

A very common interview question — know this cold.

flowchart LR L["Login"] --> Auth["Authentication\n('Who are you?')"] Auth --> Authz["Authorization\n('What are you\nallowed to do?')"] Authz --> R["Access Resource"]
Authentication Authorization
Question "Who are you?" "What are you allowed to do?"
Examples Username, Password, MFA, Fingerprint Read VM, Delete VM, Create Storage

🧠 Interview Angle: "Authentication verifies identity. Authorization determines permissions after identity is verified."

4.5 Service Principal

Very important for DevOps engineers. A Service Principal is a non-human identity used by applications and automation tools to access Azure — instead of a person logging in, the automation itself logs in.

flowchart LR TF["Terraform Pipeline"] --> SP["Service Principal"] --> AL["Azure Login"] --> Deploy["Deploy Infrastructure"]

Used by: Terraform, Azure DevOps, GitHub Actions, Ansible, automation scripts. Benefits: secure automation, no personal account tied to it, works 24×7 unattended.

🧠 Interview Angle: "A Service Principal is a non-human identity used by applications and automation tools to securely access Azure resources."

4.6 Managed Identity

Another critical interview topic. A Managed Identity is an identity Azure creates and manages automatically — no username, password, secret, or certificate for you to handle at all.

🏢 Real Project Example: A VM needs to access Key Vault. Instead of storing a secret inside the VM, enable a Managed Identity on it, grant that identity access to Key Vault, and the VM connects securely — no credentials anywhere.

Type Description
System Assigned Tied to one resource; created and deleted together with it
User Assigned Created separately; can be attached to multiple resources

Service Principal vs Managed Identity

Service Principal Managed Identity
Credentials Requires a secret or certificate No secret required
Usable outside Azure Yes Azure resources only
Credential management Manual Azure-managed automatically
Best for CI/CD pipelines Azure-to-Azure resource access

4.7 App Registration vs Enterprise Application

A commonly confused pair — remember it this way:

💡 Tip: App Registration = the developer creates the app's identity. Enterprise Application = the organization actually uses that app.

  • App Registration creates an identity for an application so it can authenticate with Microsoft Entra ID. It provides: Application ID, Tenant ID, Authentication, API Permissions, Client Secret (if needed).
  • Enterprise Application represents how that application is used inside your organization — e.g. Salesforce, GitHub, ServiceNow, and SAP all appear as Enterprise Applications once integrated with Entra ID.

4.8 Multi-Factor Authentication (MFA)

MFA requires more than one verification method — e.g. Password + Mobile OTP or Microsoft Authenticator. Even if a password is stolen, an attacker still can't log in without the second factor.

4.9 Conditional Access

Conditional Access enforces login rules based on user, location, device, or risk level. Example rules: only allow login from the office network, only from a company-managed laptop, block high-risk countries, require MFA, block legacy authentication.

🏢 Real Project Example: A developer tries logging in from another country — Conditional Access blocks the login automatically, even with the correct password.

4.10 Privileged Identity Management (PIM)

PIM provides Just-In-Time (JIT) privileged access — users don't hold admin rights permanently; they request access only when needed, for a limited time.

🏢 Real Project Example: A DevOps Engineer needs the Owner role → requests it via PIM → gets approved → receives Owner access for 2 hours → access is automatically removed afterward.

Benefits: improved security, full audit trail, least privilege enforced, temporary (not permanent) admin access.

Real Identity Flows

flowchart LR Pipe["Azure DevOps Pipeline"] --> SP["Service Principal"] --> Entra["Entra ID"] --> ARM["Resource Manager"]

✅ Part 4 Best Practices

  • ✅ Enable MFA for all users.
  • ✅ Use Groups, not individuals, for permission assignment.
  • ✅ Use Managed Identity for Azure-resource-to-Azure-resource access.
  • ✅ Use Service Principal for CI/CD automation (Terraform, pipelines).
  • ✅ Avoid using the Owner role unless truly necessary.
  • ✅ Use PIM for any privileged/admin role.
  • ✅ Apply Conditional Access policies for login security.

🖥️ Hands-On: Create a User in Microsoft Entra ID

  1. In the Azure Portal search bar, type "Microsoft Entra ID" and open it.
  2. Select Users from the left menu, then + New user → Create new user.
  3. Fill in the User principal name (e.g. amit@yourcompany.onmicrosoft.com), Display name, and password options.
  4. Optionally assign the user to a Group and a Role right away.
  5. Select Review + create, then Create.

💡 Try it yourself: After creating the user, go to Groups → + New group → create a "DevOps Team" group → add the new user as a member → then assign Contributor RBAC to the group (at a Resource Group scope) instead of the individual user. That's the real-world pattern almost every enterprise uses.

🧠 Part 4 — Interview Questions

What is Microsoft Entra ID?

Azure's cloud-based Identity and Access Management service, used to authenticate users and applications and manage their access to Azure resources. Formerly known as Azure Active Directory.

What is Identity?

The information that uniquely identifies a user, application, or service before Azure grants it access to resources.

What is the difference between Authentication and Authorization?

Authentication verifies who you are (login credentials, MFA). Authorization determines what you're allowed to do once your identity is confirmed.

What is a Service Principal?

A non-human identity used by applications and automation tools — like Terraform or a CI/CD pipeline — to securely authenticate and access Azure resources.

What is Managed Identity?

An identity automatically created and fully managed by Azure, with no username, password, or secret for the user to manage — used by Azure resources to access other Azure resources securely.

What is the difference between System Assigned and User Assigned Managed Identity?

System Assigned is tied to a single resource and deleted along with it. User Assigned is created independently and can be shared across multiple resources.

What is MFA?

Multi-Factor Authentication — requiring more than one verification method (e.g. password plus a mobile OTP) before granting access, so a stolen password alone isn't enough to log in.

What is Conditional Access?

A policy engine that enforces login rules based on conditions like user, device, location, or risk level — for example, requiring MFA or blocking logins from unapproved countries.

What is PIM (Privileged Identity Management)?

A service that provides Just-In-Time, time-limited privileged access instead of permanent admin rights — users request elevated access only when needed, and it's automatically revoked afterward.

What is App Registration?

The process of creating an identity for an application so it can authenticate with Microsoft Entra ID — it provides an Application ID, Tenant ID, and API permissions.

🧩 Part 4 — Scenario-Based Questions

Your Terraform pipeline needs to deploy Azure resources automatically. Which identity will you use?

A Service Principal — CI/CD tools like Azure DevOps and GitHub Actions need a non-human identity to authenticate with Azure without a person logging in manually.

An Azure VM needs to access Azure Key Vault securely without storing passwords or secrets inside the VM. What will you do?

Enable a System Assigned Managed Identity on the VM and grant it the required permissions on the Key Vault — this removes the need to store any credentials at all.

Your company wants administrators to have Owner access only during maintenance windows. How will you implement this?

Use Privileged Identity Management (PIM) so administrators can request temporary Owner access, which is automatically removed after the approved duration expires.

A user logs in successfully but still cannot delete a virtual machine. Why?

Authentication succeeded, but the user lacks the required RBAC permission — for example, they only have the Reader role. Authentication confirms identity; authorization determines what actions are allowed.

Users must log in only from company-managed devices and always complete MFA. Which Azure feature will you use?

Conditional Access — configured to require compliant devices and enforce MFA before granting access.

📋 Part 4 — Quick Revision

  • Identity = a user, application, or service accessing Azure.
  • Microsoft Entra ID = the Identity and Access Management service for the whole Tenant.
  • User = a person's identity. Group = a collection of users, used for scalable RBAC.
  • Authentication = verifying identity. Authorization = verifying permissions.
  • Service Principal = non-human identity for apps/CI-CD, needs a secret/certificate.
  • Managed Identity = Azure-managed identity for Azure resources, no secrets needed.
  • System Assigned MI = one resource, deleted with it. User Assigned MI = reusable across resources.
  • App Registration = creates an app's identity. Enterprise Application = how that app is used in your org.
  • MFA = multiple verification factors. Conditional Access = policy-based login control.
  • PIM = temporary, Just-In-Time privileged access.
